# The site's chrome paints with the simulations' own palette (palette superseded by 0010)

> The palette in this ADR was replaced by `docs/adr/0010`. The rules about tokens and the printable sheet still hold.

The site's own pages take their colours from the simulations, under the names the simulations already use: `--bg`, `--surface`, `--text`, `--text-muted`, `--link`, and so on. The chrome and the thing it frames are one surface, so an embedded simulation is not a rectangle punched through the page. Before this the chrome was `#111111` and the simulations `#0a0a1a` — both dark, close enough to pass unnoticed and different enough to draw a seam exactly where the reader is looking.

The values are written into `src/lib/theme.ts` rather than read out of a simulation at build time. A simulation file is content this site does not own and does not edit (ADR 0005), so deriving the site's appearance from it would make the chrome depend on a file that gets replaced without notice. A test reads the simulation files and asserts the two agree, which is the check that would notice.

**The chrome follows the simulations; it does not lead them.** The simulations ship a complete light palette under `[data-theme="light"]` and select the dark one by writing `data-theme="dark"` on the `<html>` element. Measured across all 23: every one is hardcoded dark, none reads `prefers-color-scheme`, and no script changes the attribute. The chrome paints with the dark half and does nothing about the light one, because the ticket asks that the chrome follow the simulations if they ever honour a preference, not that it anticipate it.

That is a claim about reversibility, so it is worth being precise about what makes it true. `themeCustomProperties` takes the palette *and* the selector it writes it under, so adding the light half is one call under `[data-theme='light']` with the other half of their palette — not a restructuring of how the chrome is coloured. No such block is emitted today, and writing one now would be the chrome leading the simulations: a light page framing a hardcoded-dark simulation, which is the exact seam this ticket exists to remove.

**The accent is a border colour, never a text colour.** The simulations' `--accent` reaches 4.2:1 against the page background, which is under the 4.5:1 that body text needs. That is why they only ever use it on borders and never on running text, and the chrome does the same. A test asserts the accent stays below the text ratio, so it cannot quietly be reached for as a link colour.

**One colour per meaning, everywhere.** A page writes `var(--text-muted)` rather than repeating a value, and a rule on `a` itself gives every link the palette's link colour. That last rule exists because of a specific failure: the "open in a new tab" link on every simulation page had no colour of its own and rendered in the browser's default link blue, `#0000ee` on `#111111` at 1.4:1. A link in a component that styled everything around it and not the link is the shape that produced the only contrast failure on this site, and a rule on the element is what stops it recurring.

**The frame carries no edge of its own.** It is painted the page background, so the seam with the simulation has no contrast to draw, and its border is the shared hairline rather than something brighter than both sides. A border brighter than the page *and* the simulation would draw exactly the edge the ticket says not to draw, even with both backgrounds matched.

**The focus ring is one rule, drawn with an outline.** An outline does not move the layout, so focusing cannot make a control jump, and the ring's colour is held to the same 3:1 as every other non-text element on the site. The browser's own outline is a grey chosen for whatever it thinks the page looks like, which on this background fails that bar.

Measuring the focus behaviour changed what was written. Tabbing into the frame moves the keyboard *inside* the simulation, not onto the frame element: the host is `document.activeElement` but matches neither `:focus` nor `:focus-visible`, and the focused node is inside the simulation's own document. A ring bound to `:focus` on the host would therefore never appear. The ring is drawn on `:focus-visible`, and what a reader actually sees when they tab into a simulation is the simulation's own focus indicator — which is the correct thing to trust, since it is the element that has focus.

The printable sheet is the one exception to the no-literals rule. Its print stylesheet keeps literal values because a printed page carries no custom properties into it: ink on paper, not screen colour.
